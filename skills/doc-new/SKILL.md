# 設計文書を残す

決めた直後に呼ばれる。数分で終わらせること。長い聞き取りにしない。

書式の正典は `${CLAUDE_PLUGIN_ROOT}/reference/format.md`。**最初に必ず読む。**
ひな形は `${CLAUDE_PLUGIN_ROOT}/templates/` にある。

文書の置き場所は、環境変数 `CLAUDE_PLUGIN_OPTION_DOCS_DIR`、無ければプロジェクト直下の
`.speclink.json` の `docsDir`。どちらも無ければ、置き場所をユーザーに尋ねて `.speclink.json` を作る。

## 手順

1. **種類を決める** — 要件 / ユースケース / 決定のどれか。迷ったら「決定」。
   会話の流れから判断できるなら聞かない。
2. **下書きを作る** — 会話に出た内容だけで埋める。
3. **足りないものを聞く** — 下記の「必ず聞くこと」だけを 1 回でまとめて聞く。
4. **範囲指定を提案する** — コードを見て、どのファイル・どの項目に効くかを挙げ、確認を取る。
   フォルダ全体を指さない。狭めに出す。
5. **保存する** — `<docs>/<種類>/<id>-<短い名前>.md`。id は既存の最大値 + 1。
6. **索引を更新する** — `node "${CLAUDE_PLUGIN_ROOT}/scripts/build-index.mjs"` を実行する。
   範囲指定が粗いと警告が出る。出たら直す。

## 必ず聞くこと

**却下した案とその理由**。会話に出ていなければ必ず聞く。これがこの文書の中心で、
コードからも履歴からも復元できない唯一の情報。

答えが「特に無い」なら空欄のままにする。**推測で埋めない。**

要件を書くときは、業務の事情（誰が何に困っているか・客先との取り決め）も同じ扱い。
本人が言っていないことを書かない。

## やらないこと

- コードを読めば分かることを書く（画面の項目一覧・処理の流れ）
- 操作手順を書く（画面を変えた瞬間に嘘になる）
- 索引を手で書く（自動生成に任せる）
- 既存文書の書き換えを勝手にやる（`/doc-sync` で提案し、判断は人に委ねる）

## 既存の決定と衝突したとき

同じ範囲に `active` な決定があり、今回それを覆すなら、古い方を `status: superseded` にして、
新しい文書に `supersedes` を書く。古い文書は消さない。
