# 設計文書に残す

**呼ばれ方は 2 通り。** どちらも同じ手順で動く。

- コミット前の確認（speclink の関所）が反応したとき、**Claude が自分で実行する**（主）
- 人が明示的に `/doc-new` と打ったとき（従）

人は「決めるたびにコマンドを打つ」ことをしない。それを前提に組む。
**人に聞くのは、人しか知らないことだけ**にする。種類・置き場所・ファイル名は聞かない。

書式の正典は `${CLAUDE_PLUGIN_ROOT}/reference/format.md`。**最初に必ず読む。**
ひな形は `${CLAUDE_PLUGIN_ROOT}/templates/`。
文書の置き場所は `CLAUDE_PLUGIN_OPTION_DOCS_DIR`、無ければプロジェクト直下の
`.speclink.json` の `docsDir`。どちらも無ければ `/doc-init` がまだなので、それを案内して終わる。

## 手順

### 1. 何を残すかを自分で決める

会話とコードの変更から判断する。**聞かない。**

| 残すもの | 判定 |
| --- | --- |
| ユースケース | 担当者ができることが増えた／変わった |
| 決定 | 作り方に選択肢があり、何かを却下した |
| 何も残さない | 表示項目が増えただけ・体裁を直しただけ・内部の整理だけ |

**「何も残さない」が多数派になるのが正常。** 迷ったら残さない側に倒す。
コードを読めば分かることを書くと二重管理になり、仕組みごと信用を失う。

要件（業務の事情）はここでは作らない。コミットからは生まれない。

### 2. 既存の文書を探す

対象範囲（`scope.paths` / `scope.fields`）で照合し、該当する文書があるかを見る。

- **ある → 更新**（手順 3-A）
- **ない → 新規**（手順 3-B）

### 3-A. 更新する

**書き換え案を先に見せ、承認を取ってから書く。** 黙って書き換えない。

```
UC-12 の更新案

  ## 何を達成する
- 単価を直せる
+ 単価を、一覧を離れずに直せる

  ## 業務ルール
  （既存の行は触らない）

この内容で更新しますか？
```

- 直すのは**変更で実際に変わった箇所だけ**。ついでの整形をしない
- 業務ルール・想定外の流れなど、人が書いた行は勝手に消さない
- 決定文書も更新してよい（2026-08-09 決定）。ただし**却下した案とその理由は消さない**——
  この仕組みが防ごうとしているのは「同じ議論の繰り返し」なので、そこを消すと本末転倒になる

### 3-B. 新規に作る

1. 会話とコードから下書きを作る
2. **対象範囲を決める** — ファイル名まで、できれば項目名まで。フォルダ全体を指さない
3. 保存する — `<docs>/<種類>/<id>-<短い名前>.md`。id は既存の最大値 + 1

### 4. 人に聞く（1 回だけ）

聞くのは**人しか知らないこと**に限る。まとめて 1 回で聞く。

- **却下した案とその理由**（決定を残すとき。会話に出ていれば聞かない）
- 業務上の制約で、コードから読み取れないもの

答えが「特に無い」なら空欄のまま残す。**推測で埋めない。**
聞くことが無ければ何も聞かずに進める。

### 5. 索引を更新する

```
node "${CLAUDE_PLUGIN_ROOT}/scripts/build-index.mjs"
```

範囲指定が粗いと警告が出る。出たら直してから終わる。

### 6. 一言で報告する

何をどこに残したか、空欄のまま残した項目は何か。長く書かない。

## やらないこと

- コードを読めば分かることを書く（画面の項目一覧・処理の流れ・関数の説明）
- 操作手順を書く（画面を変えた瞬間に嘘になる）
- 却下理由・業務の事情の創作（聞くか、空欄で残す）
- 種類・置き場所・ファイル名を人に確認する（自分で決める）
- 索引を手で書く（自動生成に任せる）
- 何も決まっていないのに文書を作る（多数派は「何も残さない」）
