# 文書置き場の立ち上げ

導入時に一度だけ実行する。**聞くのは置き場所だけ**。あとは既定で進める。
質問を並べて確認を取らない（立ち上げが止まると、そのまま使われなくなる）。

書式の正典は `${CLAUDE_PLUGIN_ROOT}/reference/format.md`。**手順 2 の前に必ず読む。**

## 手順

### 1. 置き場所を決める

引数があればそれを使う。無ければ `../<プロジェクト名>-docs` を提案し、確認を 1 回だけ取る。
プロジェクトの中に置かない（決定は複数のリポジトリにまたがるため、対等な場所に置く）。

```
node "${CLAUDE_PLUGIN_ROOT}/scripts/init-docs.mjs" <文書ディレクトリ>
```

フォルダ・README・プロジェクト側の `.speclink.json` ができる。
バージョン管理は文書ディレクトリで `git init` する（リモートは後で本人が繋ぐ）。

### 2. ユースケースの草案を起こす

画面・ルートの構成を調べ、**担当者が 1 回座って達成したい 1 つのこと**の単位で起こす。

- 題名は「誰が、何を、どうできる」。画面の作りを書かない（画面を変えたら嘘になる）
- 範囲指定（`scope.paths` / `scope.fields`）を埋める。**ファイル名まで、できれば項目名まで**。
  フォルダ全体を指さない
- 本文の「業務ルール」「想定外の流れ」は**空欄で残す**。コードから復元できない情報なので、
  推測で埋めない（`/doc-new` で後から本人に聞いて埋める）
- 1 つのアプリで 15〜25 件が目安。超えるなら割りすぎ

ひな形は `${CLAUDE_PLUGIN_ROOT}/templates/usecase.md`。

### 3. 要件の骨格を起こす

ユースケースを束ねる上位の要件を、**題名と所属だけ**作る。
中身（誰の何が困っているか・業務上の制約）はコードにも履歴にも無いので空欄で残す。
ユースケース側の `parent` と相互に繋ぐ。

ひな形は `${CLAUDE_PLUGIN_ROOT}/templates/requirement.md`。

### 4. 既存の決定を移す

プロジェクト指示（CLAUDE.md）・`docs/` 配下・設計メモに、過去の決定が書かれていることが多い。
これを決定文書へ移す。

- **転記だけ。書かれていないことを足さない。**
- 却下した案と理由が元の記録にあれば、それを最優先で写す（この文書の中心）
- 無ければ空欄のまま残す。推測で埋めると、文書全体が信用できなくなる
- 元の記録は消さない。移設の判断は本人に委ねる（この手順では触らない）
- 覆された決定は `status: superseded` にし、新しい方に `supersedes` を書く

ひな形は `${CLAUDE_PLUGIN_ROOT}/templates/decision.md`。

### 5. 索引を作る

```
node "${CLAUDE_PLUGIN_ROOT}/scripts/build-index.mjs"
```

範囲指定が粗い文書があると警告が出る。**出たら必ず直してから終わる**（粗いまま始めると、
毎回関係ない文書が差し込まれて読み飛ばされるようになり、仕組みごと死ぬ）。

### 6. 報告する

作った件数と、**空欄で残した項目**を伝える。空欄は放置してよいものではなく、
「本人しか書けないので後で `/doc-new` で埋める」対象だと明示する。

## やらないこと

- 業務の事情・却下理由の創作（元の記録に無ければ空欄）
- 操作手順の記述（コードが正本）
- 画面の項目一覧の書き写し（コードが正本）
- 索引の手書き（自動生成に任せる）
- 元の決定ログの削除・書き換え
